# Protocol revision 4 — 20 cases per candidate, Claude Code adjudication

Study-owner decision: `FINAL_TILEBENCHPP_LLM_EXECUTION_PROMPT_2026-10-07.md`. Revision 4 keeps every
revision-3 decision and changes the task unit, the evaluator, the review policy and several shared
components. Revision 2 (`formal_b200_base_2026-10-06`) and revision 3
(`formal_b200_base_1dtype5r_2026-10-06`) campaigns are pilots: `manifests/excluded_campaigns.yaml`
refuses them in code for formal metrics, distillation (evaluation and release), Enhanced pairing,
release-skill sources, resume, review and re-evaluation. Their artifacts are kept unchanged.

## 1. Unchanged (revision 3)

- one predeclared representative dtype per operator (`representative_dtypes.yaml`, unchanged mapping:
  35 fp16, 6 fp32, 2 int8, 2 int32);
- exactly 5 rounds per trajectory, exactly 1 candidate generation per round, no same-round repair;
- every sent generation is charged (tokens and USD), whatever its outcome;
- runtime-only performance feedback; no performance early stop;
- generators: GPT `gpt-6.1-sol`, `reasoning.effort=xhigh`, `max_output_tokens=128000`; Claude
  `claude-opus-5-5`, `output_config.effort=xhigh`, adaptive thinking, `max_tokens=128000`;
- Base and Enhanced identical except the frozen Optimization Skill;
- no backend/runtime autotuning, no hidden empirical configuration search;
- timing: 1 warmup + 3 timed launches, LLC flush outside the timed scope, CUDA-graph replay on NVIDIA,
  formal capture-failure policy `timing_error`.

## 2. Task identity: 45 operators x one dtype x all 20 configured cases

A formal trajectory task is `(operator, selected dtype, device, DSL, model, condition)`. Each generated
candidate source is evaluated on ALL configured cases of the selected dtype, frozen in
`manifests/case_sets.yaml` (45 operators x 20 cases; `case_id`, params, problem size, dtype and the hash of
the config's case sections; generated by `tasks.case_sets.build_manifest`, validated against the configs on
every load; nothing synthesized). The trajectory's `case_id` is the frozen case-set id; Base and Enhanced
use the identical case IDs. Generation does not multiply by 20: B200 Base = 45 x 3 DSLs x 2 models x 5
rounds = 1350 nominal generator calls.

The generator sees the operator semantics, the dtype, the interface, the canonical contract, the generic
device context and the case suite's **parameter domain** (constants and, per varying parameter, its integer
range and common divisor; `tasks.case_sets.domain`), never the case list. It is told that configuration may
be a deterministic function of the input shapes and that runtime timing/search/autotuning and tables keyed to
particular benchmark shapes are not allowed. It never sees per-case Torch time, per-case kernel time, T_emp,
efficiency, speedup or ranking.

## 3. Contract migration (contract revision 3)

27 of the 45 `contract.md` carried single-fixed-shape wording ("the task's fixed `n`", "supporting shapes
other than the task's declared shape is not required", "the task's declared shape has `W == H`", ...). A
mechanical migration (`docs/llm_v2/contract_revision_3_changes.json`, 68 replacements) rewrote only those
clauses to the configured cases ("a case's `n`", "outside the task's configured cases", "every configured case
has `W == H`"), keeping the canonical algorithm, stages, precision and every legitimate domain constraint
(each domain claim was checked against the 20 cases). No manual kernel was re-extracted; no pilot outcome was
used. Changed contracts are `contract_revision: 3` with the previous `contract_sha256` and the decision in
`audit.json` (`revision_3`); `evaluator_rules.json` are unchanged.

## 4. 20-case evaluator

`evaluation.worker` loads the candidate once in one isolated worker (bwrap, device lock, wall clock
3600 s for the whole suite) and evaluates the cases in order. Per case: fresh inputs, first execution
(compile/specialize), `get_last_config()` read after the first execution, the numerical checks and timing (a
change within one case is that case's `interface_error`; different cases may report different deterministic
configurations), three numerical checks (fresh, same-address refill, repeat; undeclared mutation and output
aliasing fail), 1 warmup + 3 timed launches, three raw samples and their mean, timing mode, diagnostics.
Each finished case is appended to `cases.jsonl` before the next starts.

Round rules: valid only with 20/20 valid cases; round latency = geometric mean of the case means (recomputed
by the state machine, which refuses an inconsistent suite). A contract violation or a compile failure of a
case stops the suite (the remaining cases are `not_evaluated`, never fabricated); other per-case failures are
recorded and the next case runs. A worker that dies (timeout, crash, OOM kill) keeps the finished cases; the
case it was working on is the failing one; the round is invalid (`runtime_error`), not a framework failure.
The launcher records the cgroup `memory.events` OOM counters before/after each evaluation
(`resources.cgroup_oom_kill_delta`).

## 5. Feedback and metrics

Generator feedback: `valid on k of 20 cases`, the geometric-mean runtime of valid rounds, a concise
diagnostic and, for an invalid round, the semantic parameters of the first failing case; the configurations
the candidate reported (distinct values, no case mapping). Per-case raw measurements are stored for offline
analysis only.

Metrics (offline): `speedup_ij = T_torch_j / T_ij` (stored CSV baseline, `artifacts/llm_v2/baselines/`, never
re-measured) and `eff_ij = T_emp_j / T_ij`; round-level geometric means over the 20 cases; one equal-weight
curve per operator; `E(B)` = best valid round-level geomean efficiency with cumulative generator cost <= B;
`E_bar(B)` = arithmetic mean over the 45 operators; token and USD axes separate; unknown usage stays unknown.
The B200 scoring table has 900 rows, all `ok` (`artifacts/llm_v2/scoring/B200/scoring_table_B200_rev4_casesets_2026-10-07.json`).

## 6. PrecisionGuard fix

Revision 3 closed 16 rounds as `contract_violation` with `cuda.matmul.fp32_precision: ('none', 'ieee')`
although none of the candidates touched precision settings: the matmul_int8 / linear_self_attention references
set the LEGACY `allow_tf32` inside `run()`, which in torch 2.10 writes the new `fp32_precision` field; the guard
restored only legacy fields and then blamed the candidate. The guard now snapshots, restores and verifies one
canonical family (`fp32_precision` on torch >= 2.9: backends / cuda.matmul / cudnn / cudnn.conv / cudnn.rnn plus
the non-overlapping flags), restores the stored legacy global first and the new fields last, and checks the
restore (an evaluator failure is `infrastructure_incomplete`, never the candidate's). Regression: the 16 archived
candidates replayed on B200 are all `valid`, 0 precision violations
(`artifacts/llm_v2/precision_guard_regression/replay_16_2026-10-07.json`); synthetic candidates that change
legacy TF32, the new API, `set_float32_matmul_precision`, cuDNN TF32, the default dtype or deterministic mode are
still violations (`tests/llm_v2/test_protocol_v4.py`).

## 7. Checker v3 (`contract_checks/2026-10-07.v3`) and v4 (`contract_checks/2026-10-07.v4`)

Generic, AST/token-based (no candidate whitelist):
- a regex match that spans a line break is not evidence unless the rule declares `multiline: true`;
- a match containing `@` is the matrix-multiply operator only where the AST has a MatMult expression; decorators
  never are; a host `a @ b` on tensors stays a confirmed violation;
- a forbidden term that occurs only inside a name the candidate defines (function/kernel/variable/parameter) or a
  keyword-argument name (`block_shape=`) is not delegation; imports and imported objects stay evidence;
- `.contiguous()` under an `is_contiguous()` test is audit-only;
- a module-level cache whose stored value is a compiled kernel or function object is a code cache (audit), not a
  tensor/output cache; a cache storing tensors keyed by data/address stays review;
- a missing positive evidence pattern stays audit-only.
Regression on the 1144 archived pilot candidates (`artifacts/llm_v2/checker_v3_regression/`): 31 of the 32
pilot reviews become audit-only (the remaining one, a matmul_int8 transposed copy permitted only per call, is a
genuine review); the revision-3 `confirmed_violation` of a candidate whose own function was named
`_flash_attn_fwd` becomes audit-only; no new review or violation.

Checker v4 (found during the first formal launch's reviews, see §11): the cache data-flow seeded EVERY `run()`
parameter not annotated as a scalar as a tensor argument, so a per-call configuration dict holding a launch grid
computed from scalar inputs (`run(input, N, C, H, W, kernel_size, stride, padding)`) went to review; 25 of the 45
interfaces pass Python numbers. v4 reads the frozen kinds of the task's positional `run()` inputs
(`manifests/input_kinds.yaml`, derived by calling each operator's input generator on all 20 frozen cases, identical
across cases; part of the checker fingerprint): a parameter whose position receives a Python number is configuration,
not a tensor seed. Tensor inputs, outputs and anything torch-produced stay tensor-derived. Regression on all 1161
archived candidates (`artifacts/llm_v2/checker_v4_regression/`): only the 4 reviews of the aborted launch change (3
clear, 1 audit-only); no candidate becomes stricter; the genuine revision-3 review stays.

## 8. Compliance review: Claude Code adjudicates

`study.yaml compliance.adjudicator: claude-code`. A genuine `review_required` item is decided by the
supervising Claude Code session (no reviewer API call, no human dependency) from the candidate source, the
frozen contract, the evaluator rules, the exact checker evidence and the task interface only
(`python -m tilebench.llm.v2 review-packet`, which asserts the absence of latency/speedup/T_emp/cost fields).
`review-resolve --decision compliant|violation --note <rationale>` (reviewer defaults to `claude-code`; a formal
trajectory refuses any other adjudicator) records reviewer, candidate/contract/rules/checker hashes, evidence,
decision, rationale and timestamp in the round (`reviews`) and in `reviews.jsonl`. Compliant: the archived
candidate is evaluated, no new generation. Violation: the round closes as `contract_violation`; the next round
receives the diagnostic. A contract/checker bug found during review pauses the campaign and is versioned; a
frozen contract is never rewritten mid-campaign (review-resolve refuses when the contract hash changed).

## 9. Usage and USD

Raw provider usage is archived unchanged; the normalized record (`normalized_usage/2`) adds, nullable:
provider/model/response id, service tier, inference geo, logical input total, uncached / cached / cache-write
input, logical output total, reasoning-or-thinking output (a SUBSET of output, never added again), non-reasoning
output, reported total, server-tool counts and cache diagnostics. OpenAI fields read: `input_tokens`,
`input_tokens_details.{cached_tokens,cache_write_tokens}`, `output_tokens`,
`output_tokens_details.reasoning_tokens`, `total_tokens`, `service_tier`, `prompt_cache_key`/`prompt_cache_retention`
when present. Anthropic: `input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`,
`cache_creation.ephemeral_{5m,1h}_input_tokens`, `output_tokens`, `service_tier`, `inference_geo`,
`server_tool_use`; `output_tokens_details.thinking_tokens` and a non-null `diagnostics` are read when returned
(the installed SDKs keep unknown fields; anthropic 0.103.1 / openai 2.37.0 needed no upgrade). The frozen pricing
snapshot (`api_pricing.yaml`) is unchanged; per transport attempt the USD record keeps the snapshot hash, rule id,
components, total, lower bound and status. Claude Code adjudication has zero API cost.

## 10. Pipeline

One `schedule` process runs every (model, DSL) track (`--models gpt claude --dsls triton cutile tilelang`):
per-provider adaptive concurrency (3 -> 6 -> 12 ..., 429 Retry-After/reset, sustained-overload backoff) and ONE
global hard evaluation-backlog budget (`--max-pending-evaluations`, default 16): a trajectory reserves a slot
atomically before its generation request is sent and releases it when the round closes, so generated + waiting +
in-evaluation candidates never exceed the cap. Round i+1 of a trajectory waits for its own round-i evaluation;
other trajectories generate while the device evaluates. The concurrency ramp is gated on the evaluation backlog
(candidates waiting for or in evaluation), not on the budget reservations of trajectories still waiting to send (the
first formal launch stayed at 3 per provider because of that, §11). STOP / STOP_<model> pause gracefully; resume only
under the exact frozen identity.
