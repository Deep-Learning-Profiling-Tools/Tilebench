# Extended Blind Analysis Evaluation

## Assessment

Deterministic extraction is much more reliable than free-form factual wording in
this pilot. The six frozen v4 trials preserved all 8,178 numeric NCU records and
produced no independently detected SASS instruction-count errors. Both repeats
for each operator identified the same broad code/resource pattern and qualified
exact causality. Reference-backend wording still needed review.

The additional v5 forward check passed all 867 records, for 9,045/9,045 across
seven new analysis runs. Automatic ranking fixed the reference labels in that
run, but its prose introduced a separate tail-effect overstatement.

This supports a small skill plus evidence readers and validation, not a claim
that an unattended agent can publish a correct causal analysis for any operator.

## Design

Each run used fresh GPT-6 Luna, high reasoning effort, no inherited conversation,
and a separate allowlisted detached worktree at commit
`b31f41c38c596bb29d85f66552ef13106e9087df`. No human analysis or expected mechanism
was supplied. The only substantive inputs were implementation/config/CSV records,
capture-time snapshots, raw NCU reports, an unranked exact numeric export, and the
generic skill/helpers. Separate CUDA/PTX files were withheld; SASS came from the
reports. The repeated input hashes matched except for manifest worktree paths.

Skill v4 and its two helpers were frozen before launching any analysis agent;
`freeze.json` records their hashes and the common task. The six planned trials
are two repeats each of tensor-core batched matmul, argmax reduction, and a
two-kernel histogram. Together with the original pilot, five operators have been
examined, but each extended operator has only one dtype/shape case.

An additional fresh matmul run uses v5's automatically derived reference ranking
after observing a v4 wording failure. It is an adaptive forward check, not another
independent held-out operator or randomized estimate of skill benefit.

## Repeatability And Causality

- Matmul: both runs distinguish low achieved warp/tensor activity from identical
  theoretical TileLang/Triton occupancy ceilings. They identify the different
  LDGSTS versus TMA paths and pipeline configurations, but leave exact scheduling,
  synchronization, and memory contributions unresolved. An activity gap alone
  is a symptom, not a uniquely identified cause.
- Argmax: both identify one 2048-wide TileLang chunk versus two 1024-wide chunks
  for the other winners, backed by lower dynamic instruction counts. Tile-width
  and compiler lowering remain confounded. Neither explains lower DRAM bytes as
  fewer logical input elements. Both preserve the CSV helper's ambiguous stored
  `speedup_triton` formula under printed rounding.
- Histogram: both localize the gap to the partial pass and identify shared-memory
  versus global-memory atomics in source and SASS. They do not pretend the brief
  reduce action or its high registers explains the whole-operation gap. Exact
  same-bin contention and causal contribution remain unresolved.

Agreement of these pairs is useful exploratory evidence, not a measured general
diagnosis-accuracy rate. No counterfactual compiler experiment or independent
causal ground truth was supplied.

## Remaining Errors

Matmul 1 calls cuTile the fastest non-TileLang reference even though Triton is
faster in its own table. Torch is faster still in the CSV. Its helper arithmetic
is correct, but the manually chosen comparison label is wrong. Matmul 2 correctly
includes Torch as the fastest available CSV baseline.

Both histogram reports call Triton the fastest non-TileLang backend without
restricting that phrase to the profiled DSLs. Triton is the fastest of the two
profiled non-TileLang DSLs, but Torch is faster in the supplied CSV (0.6610 versus
0.9612 ms). This is a reference-scope omission, not an incorrect Triton/cuTile
ordering. Histogram 2 also writes a 10.07x CSV ratio instead of 10.06x when rounded
to two decimals, and 20.51x for an NCU stage ratio that rounds to 20.52x. These
small prose errors do not corrupt the saved raw measurements.

The v5 matmul forward check correctly distinguishes Torch (fastest available
CSV reference) from Triton (fastest profiled DSL). Its labels and ranking were
generated automatically rather than supplied as free text. However, it says a
tail effect is not indicated because dimensions are tile-divisible. Divisibility
addresses boundary/padding tiles, not incomplete scheduling waves or imbalance
across 148 SMs for an 800-CTA grid. A wave-tail contribution is unresolved, not
excluded by divisibility alone. The ranking correction did not make the full
narrative error-free.

Two runs added metadata wrappers around unchanged SASS helper JSON despite the
requested direct backend map. The auditor normalizes these wrappers for content
checks but records the contract deviations. They are ingestion/schema issues,
not assembly-count errors. Original outputs remain unchanged.

## Helpers

The self-contained skills are under `skills/v4/tilebench-analysis/` and
`skills/v5/tilebench-analysis/`; neither is installed into the user's home skills.
They contain no operator names, shapes, measured values, or diagnosis answers.

- `csv_ratios.py`: unique row selection, explicit numeric numerator/denominator,
  finite positive validation, and conservative stored-formula matching using
  printed rounding intervals. Ambiguity is not silently resolved.
- `sass_listing.py`: NCU and addressed disassembler listings, ordinary/uniform
  predicates including `@!UP`, opcode modifiers, per-kernel static counts, separate
  NOP counts, and structured warnings for malformed rows, duplicate addresses,
  and multiple scopes.
- v5 CSV mode derives pairwise labels and fastest references automatically from
  a named target and explicit reference-column set. It preserves ties and fails
  to rank when a requested reference is invalid, rather than silently dropping it.

The initial nine helper regression tests passed, including the earlier real
Gaussian SASS undercount and CSV denominator case. Four additional ranking tests
passed. The observed need is deterministic evidence generation and checks, not
more operator-specific prompting. Numeric display tables should preferably be
rendered directly from structured facts rather than rewritten by the agent.

## Provenance And Limits

`CAPTURES.md` records fresh argmax/histogram commands, reused matmul capture, the
excluded application-replay timeout, and replay caveats. No benchmark CSVs or
autotuning were rerun. Current paper-version package pins were verified, and GPU
compute-process checks were empty before and after profiling.

The prescribed `profile/env.sh` sets CUDA_HOME to 13.2; the native compiler is
nvcc 13.2.78, while PyTorch is 2.10.0+cu130. Full native-toolchain equivalence to
CUDA 13.0 is therefore not established. A profiler's installation path is not
itself a PyTorch CUDA-runtime version record. Some agent provenance language
blurred those distinctions. The complete manifests also lack embedded package
versions/GPU UUIDs, even though the parent verified the environment and sourced
UUID pinning. Future captures should stamp these facts automatically.

Kernel replay with cache-control none can leave small inputs resident on later
passes after the harness's initial L2 eviction. NCU supports diagnosis; original
CSVs remain the benchmark timing source. Exact counts and ratios are still tied
to the supplied reports, not extrapolated to a differently compiled kernel.

Blinding excluded existing analyses and history from the input bundles, but
shared filesystem/Git access was not OS-isolated. Agent outside-directory
disclosures and command logs are self-reported. Scripts, manifests, hashes,
original outputs, and audits are retained for inspection. No commits or pushes.

```bash
  /tmp/tilebench-extended-20260930-histogram-r1 \
  --output /tmp/histogram-metric-audit.json
"$PY" profile/agent_skill_eval/20260930_extended/audit_artifacts.py \
  /tmp/tilebench-extended-20260930-histogram-r1 \
  --output /tmp/histogram-artifact-audit.json

"$PY" profile/agent_skill_eval/20260930_extended/test_reference_ranking.py -v
```

Run archived agent extraction scripts in their corresponding retained worktree;
their paths refer to that allowlisted input layout. Binary reports remain under
the operator capture directories and temporary worktrees, identified by hashes.
